# 字幕

字幕不是另做的 SRT，而是工程里的数据：识别出的字词带着源时间，跟着剪辑走。删掉一段话，它的字幕自动消失；挪动一段，字幕跟着挪。你要做的是把字改对、把断句调顺，而不是对时间轴。

## 1. 前提

- 工程有字幕轨。用 `create_project` 的 `subtitles` 建的工程已经有 `trk_sub1`；旧工程没有时，用字幕域的 `add_style` 加 `add_subtitle_track` 建，承载轨写主说话人的音频轨。
- 母稿语言与字幕轨 `language` 写法完全相同。校验报 `W_SUB_NO_TRANSCRIPT` 就是这里对不上，字幕会是空的。
- 粗剪已经批准进主工程。字幕校对在剪辑定稿后做，省得改了又被剪掉。

## 1.1 抽专有名词

识别完成后、校字之前做一次：

1. 通读文稿和 `recognition.reference_text`，挑出专有名词：品牌、产品、人名、公司和机构、地名、行业术语。普通词、口语、数字不算。
2. 识别错的名词按正确写法记，例如文稿里是「斗包」、上下文明显是「豆包」，记「豆包」，再按第 2 节改字。
3. 用 `set_recognition` 把它们追加进 `terms`（保留原有的，不要覆盖用户加的）。在本工程文稿里出现 2 次及以上的，内核会自动收进本机的全局名词库，以后的工程识别时也能认出来。
4. 告诉用户抽了哪些词，一行列完。用户说哪个不对，就从 `terms` 里删掉。
5. 名词改动很多（5 个以上识别错的）时，问用户要不要带着新名词重新识别。

## 2. 校字

桌面版在分行之后会自动跑一遍 AI 校对（第 3.2 节），只改同音错字和写错的名词。你接着校时，先看哪些字被改过（`state` 为 `edited`），不要把它们改回去。

1. `read_transcript` 按时间线读（`timeline_id`），只校会出现在成片里的字。每行开头的方括号里是字幕条 ID 和首尾字词 ID。
2. 对照词表逐条改：
   - 识别错的字、错的品牌名人名：`edit_text`，`from_token` 到 `to_token` 换成正确文字。原来听到的内容会自动存进 `heard`，不会丢。
   - 数字统一写法：采访里的数字按词表或用户偏好统一，例如「百分之六十」写成「60%」。拿不准用户偏好就问一次，然后全片统一。
   - 口头禅和语气词：字幕里可以不显示，但画面里还在说。用 `hide_tokens` 隐藏，不要用剪辑去删。
3. 听不清、可能说错的地方（尤其是数字、人名、专有名词），不要猜。加 `review` 标记，写明「12 分 03 秒：识别为『三千万』，请核对」。标记是剪辑域操作，单独一个请求。
4. 每批改动一个 `edit` 请求，按段落分批，方便撤销。

## 3. 断句

识别出来的字词没有标点，程序只能按停顿和字数切，切出来的不能用。字幕的每一个断点都由 AI 按意思决定（`subtitle-rules.md` 第 10、11 节，ADR-0021）。

**桌面版里不用你做**：宿主进程在识别完成后自动整理，字幕面板显示「AI 整理字幕…」。你识别完等它结束再看字幕，不要自己再跑一遍。

**桌面版里要重新分行或校对**（用户说「这几条重新分一下」「再校一遍错字」）：调用 `subtitle_tidy` 或 `subtitle_proofread`，范围用 `cue_ids`，用户的要求原话放进 `request`。不要自己读字词、自己切。两个动词立刻返回，进度看 `ui_state` 的 `subtitle_pass`，跑完历史里多一步。见 `subtitle-editing.md` 第 2 节。

**命令行和 MCP 里你来做**：

1. 识别完，读母稿的字词（第 2 层 `text` 非空的），按顺序每块不超过 600 个字词。
2. 每块按下面的要求切成字幕行，开了去除水词（`recognition.remove_fillers`）时去掉水词。
3. 把每行对应到字词：每行最后一个字词进 `cut_after`，去掉的字词进 `hide_tokens`。
4. 一个 `edit` 批次提交：先 `hide_tokens`，再一个不带 `range`、带全部 `cut_after` 的 `resegment`，`label` 写「AI 整理字幕」。内核只在你给的位置断开，不会替你再切，所以每行都要符合要求。
5. 之后改了字，对改动的那一段重新给 `cut_after`。

### 断句要求

下面这段同时是桌面版发给 Agent 的提示词，改的时候和宿主代码一起改。

> 你在给一段中文口播或采访做短视频字幕。输入是语音识别的原文，没有标点。你的任务是把它切成一行一行的字幕：**只切，不改字**，不加标点，不调整顺序。
>
> 输入里的「/」表示说话人停了一下，「//」表示停了较长时间。停顿只是参考：说话人常在半句中间停，也常一口气说完两句。断点按意思定。
>
> **一行字幕是一个意群**：观众只看这一行就能明白它在说什么，不用等下一行。
>
> 1. 每行不超过 `max_chars` 个字，目标 8 到 14 个字。宁可短一点，也不要为了凑字数把下一句的开头拉进来。
> 2. 在这些地方断：一句话说完的地方；主语说完、后面是一大段谓语的地方；「先……然后……」这样的并列动作之间；说话人自我纠正、改口的地方。
> 3. 连接词放在下一行开头：但是、然后、所以、因为、如果、而且、就是说、比如、其实、那、好。口语里单独的「好」「对」「那」常常表示开始新的一句，例如「好这个词要这样说」应该是「好这个词要这样说」一行，前面的内容另成一行。
> 4. 每行结尾必须是说完的：不以「的、地、得、和、与、在、是、把、被、给、对、让、很、都、也、就、这个、一个、需要、可能、就是、能够、可以、要、会、去、帮我们、给到、这么一个」结尾。「的」只有在「是……的」或句子真的说完时才能放结尾。
> 5. 每行开头不能是「了、着、过、吗、呢、吧、们、上、里、时」。
> 6. 不拆专有名词、人名、品牌、数字和单位：「抖音来客」「二十四小时」「两万多个」必须在同一行。`terms` 里的词都不能拆开。
> 7. 少于 4 个字的行，除非它本身就是独立的一句（「对」「好的」），就和前一行或后一行合在一起。
> 8. 切完后从头到尾逐行检查一遍结尾和开头，再输出。
>
> **去除水词**（`remove_fillers` 为 true 时）：单独出现的「呃、嗯、啊、哎」，以及紧挨着的重复（「上传上传」只留一个，「我我我」只留一个），直接不写进行里。有意义的语气词（「好啊」「对吧」）保留。专有名词不能去掉，去掉的字不超过两成。
>
> **例子一**
>
> 输入：`所有的点位加起来可能有两万多个 / 很多的脏活全部让豆包工作去做了 // 是你要真正去使用之后你才能够去感受到`
>
> 输出：`{"lines": ["所有的点位加起来", "可能有两万多个", "很多的脏活", "全部让豆包工作去做了", "是你要真正去使用之后", "你才能够去感受到"]}`
>
> **例子二**
>
> 输入：`帮我根据商家的这个层级去出不同的内容和脚本然后分发给到他们他就会自己开始写脚本 / 好这个词要这样说这个文案好这个拍摄的场景建议是什么他都会写到这个里面`
>
> 错误的切法（按字数切，不看意思）：`和脚本然后分发给到他们他就会自己`、`开始写脚本好这个词要这样说`
>
> 正确的切法：`{"lines": ["帮我根据商家的这个层级", "去出不同的内容和脚本", "然后分发给到他们", "他就会自己开始写脚本", "好这个词要这样说", "这个文案", "好这个拍摄的场景建议是什么", "他都会写到这个里面"]}`
>
> **例子三**（去除水词）
>
> 输入：`呃 / 这个上传上传其实难度并不高但是呢就是它需要不断的有人能够去盯着`
>
> 输出：`{"lines": ["这个上传其实难度并不高", "但是呢就是它", "需要不断的有人能够去盯着"]}`
>
> 只输出 JSON：`{"lines": ["…", "…"]}`，不要解释。
>
> **修改轮**：如果输入里有「上一次的结果」和「问题」，只改有问题的行和它们前后相邻的行，其余行一字不动，仍输出完整的 `lines`。

看完 `verification.issues`：

- `W_SUB_CPS`：一条字太多、念得太快。可以在语义停顿处再断，或者隐藏不影响意思的虚词。
- `W_SUB_SHORT`：显示太短。如果和相邻条语义上是一句，`merge_cues` 合并。
- `W_SUB_TOO_WIDE`：一个词比一行还宽，通常是很长的英文名或网址，告诉用户。
- `W_SUB_PASS_FALLBACK`：桌面版的 AI 整理失败了（例如 Claude Code 登录过期），字幕还没整理好。把 `reason` 原话告诉用户。
- `W_SUB_PROOFREAD_FAILED`：AI 校对失败，分行结果还在，只是没校错字。把 `reason` 告诉用户，可以稍后调用 `subtitle_proofread` 重跑。
- `W_SUB_PROOFREAD_SKIPPED`：有几条校对改动没通过检查（改得太多），没有采用。

## 3.1 概要

桌面版识别完，和分行同时跑一次。宿主把下面这段提示词连同全片文字发给 Agent：

### 概要要求

> 你在帮视频剪辑师整理一段采访或口播的字幕。下面是语音识别出的全片文字，没有标点，可能有同音错字。
>
> 读完后输出 JSON：`{"summary": "…", "terms": ["…"]}`。
>
> - `summary`：不超过 200 字，说清这段视频讲什么、谁在说（身份）、属于什么领域、口吻是正式还是随意。只写文字里能看出来的，不要猜。
> - `terms`：文字里出现的人名、品牌、产品、机构、地名和行业术语，写成正确的写法。识别错了的也按你判断的正确写法写，例如文字里是「豆宝」但上下文明显在说字节的大模型，写「豆包」。拿不准的不写。
>
> 只输出 JSON，不要解释。

## 3.2 校对

分行写入后，宿主按每块不超过 80 条把字幕发给 Agent 校对，并检查返回的改动（`subtitle-editing.md` 2.2）。

### 校对要求

> 你是视频字幕的校对。下面每行是一条字幕，来自语音识别，常见错误是同音字、近音字和写错的名词。`summary` 是全片概要，`terms` 是这期视频的专有名词。
>
> 规则：
>
> 1. 只改识别错的字。不改说法，不换同义词，不润色，不调整语序。
> 2. 不加标点，不合并也不拆分行，不删口语里的重复和口头禅。
> 3. 名词按 `terms` 的写法改。`terms` 里没有、但上下文能确定的名词也可以改。
> 4. 数字保持原来的写法。
> 5. 拿不准的不改。宁可漏改，不要改错。
> 6. 有 `request` 时照它做，但不能违反上面几条。
>
> 输出 JSON：`{"fixes": [{"id": "…", "text": "改后的整行", "why": "…"}]}`，只列要改的行，`text` 是这一行改完后的完整文字，`why` 用十个字以内说明，例如「同音错字：工部→公布」。没有要改的输出 `{"fixes": []}`。只输出 JSON，不要解释。
>
> 例子：
>
> 输入：`{"summary": "字节跳动产品经理介绍豆包大模型在剪辑里的用法", "terms": ["豆包", "剪映"], "lines": [{"id": "c1", "text": "我们用豆宝来写脚本"}, {"id": "c2", "text": "然后再导到剪影里面"}, {"id": "c3", "text": "这个效果其实挺好的"}]}`
>
> 输出：`{"fixes": [{"id": "c1", "text": "我们用豆包来写脚本", "why": "名词：豆宝→豆包"}, {"id": "c2", "text": "然后再导到剪映里面", "why": "名词：剪影→剪映"}]}`

修改轮：宿主把上一次的输出和问题列表发回，例如「c7 改了 6 个字，只能改错字，不要改写」。只重新给出列出的这几行，规则不变，输出格式不变。

## 4. 片头标题和说明字

人名条、地点、片头标题这类不是说话内容的字，用 `add_free_cue` 加独立字幕条，带自己的序列时间。不要塞进母稿。

## 5. 交给人确认

- 不要把字词或字幕条设为 `approved`，那是人看过之后的状态。
- 给用户列出：改了多少处，哪些是按词表改的，哪些是你判断的，哪些加了 `review` 标记。
- 用户确认某一段没问题后，按用户的话用 `set_token_state` 或 `set_cue` 设为 `approved`，`author.kind` 写 `human`。之后重新识别或自动断句都不会再改它们。
